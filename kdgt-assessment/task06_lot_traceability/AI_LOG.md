## 3. AI 오류 발견과 수정

아래 2건은 **Claude 가 만든 1차 코드의 오류를 Claude 가 검증 과정에서 직접 발견해 고친 것**입니다.
(평가의 "직접 수정 근거"로 쓰려면 본인이 내용을 이해하고 설명할 수 있어야 합니다.)

### 오류 #1 — 동시 접속 20건 중 일부가 연결 끊김 (수정 완료)
| 항목 | 내용 |
|---|---|
| 증상 | 동시성 검증(20스레드 동시 출하)에서 `ConnectionResetError: [Errno 104]`, 검증 스크립트가 중단됨 |
| 원인 | 표준 `ThreadingHTTPServer` 의 접속 대기열(listen backlog) 기본값이 **5** 라서 동시에 20개가 접속하면 넘친 연결을 OS 가 끊음 |
| 수정 | `api.py` `_Server.request_queue_size = 128`. 검증 스크립트도 클라이언트 예외를 결과로 기록하도록 수정(중단 대신 FAIL 판정) |
| 검증 | 동시성 A/B/C 통과 |

### 오류 #2 — 제품 재검사만으로 부적합 자재가 들어간 제품이 출하됨 (설계 오류, 수정 완료)
| 항목 | 내용 |
|---|---|
| 증상 | 추적 화면 캡처를 검토하던 중, 출하 REQ-006 의 검사 근거에 `M-A #2 FAIL` 이 찍혀 있는데도 출하가 성공한 것을 발견 |
| 원인 | 1차 설계는 **LOT 자신의 상태(PASS)만** 확인했다. 원자재 M-A 가 부적합 → 제품 P-002 보류 → P-002 만 재검사 합격 → 상태가 PASS 가 되어 출하 통과. "부적합 재고 출하 차단" 위반 |
| 수정 | ① 출하·생산투입·병합 시 **검사 근거 사슬 전체**에 FAIL 이 있으면 `UPSTREAM_FAIL` 로 차단 ② 보류 시 이전 상태(`held_from`)와 보류를 건 LOT(`held_by`)를 저장 ③ 상위 LOT 재검사 PASS 시 원래 상태로 복원하고, 다른 상위 LOT 이 여전히 부적합이면 보류 유지 |
| 검증 | 시나리오 29·31·32·33단계, `test_product_reinspection_cannot_override_failed_material`, `test_release_kept_when_other_parent_still_fails`, `test_reinspection_restores_previous_status` |
| 판단 근거 | 제품 성분분석이 적합해도 원자재 MTC 가 부적합이면 압력용기 규격상 출하 근거가 되지 못한다고 보았다. 현장에서 "특채(조건부 사용 승인)" 절차가 있다면 별도 승인 기록으로 해제하는 기능을 추가해야 한다 → **현장 확인 필요** |

## 4. 동시성 검증이 실제로 의미 있는지 확인 (변이 실험)

트랜잭션을 `BEGIN`(DEFERRED)으로 바꾸고 "읽기 → 확인 → 쓰기"를 분리한 **순진한 구현**으로 일부러 교체한 뒤 같은 검증을 돌렸다.

| 항목 | 올바른 구현 | 순진한 구현 |
|---|---|---|
| 동시성 A (20×3EA, 재고 30) | PASS: 성공 10 / 부족 10 | **FAIL**: 성공 2 / 내부오류(DB 잠금) 18 |
| 동시성 B (같은 request_id 10건) | PASS: 신규 1 / replayed 9 | **FAIL**: replayed 0, 나머지 오류 |
| 동시성 C (출하 vs 부적합) | PASS | **FAIL** |

→ 검증이 그냥 통과하는 것이 아니라, 동시성 결함을 실제로 잡아낸다는 근거.
